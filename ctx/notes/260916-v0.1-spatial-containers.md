# v0.1: reverting container ownership from formal `parentId` back to spatial ("sticky") membership

## What was tried

Phase 1's questionnaire (Q5) decided the v0 migration would correct the
prototype's purely spatial container membership by adding a formal, stored
`parentId` field to every node (spec §2.3, phase2-schema.md). The intent was
to preserve the exact same user-facing behavior — drop something onto a
container and it "sticks" to it, with no UI or user-facing concept of
"assigning a parent" — while making the underlying data model less implicit.

## Why it was reverted

Implementing formal ownership meant `parentId` had to be explicitly
assigned or remapped at every single mutation site that could plausibly
change what's "inside" what:

- drop (`computeParentIdOnDrop`, drop-by-largest-overlap)
- ctrl/cmd-drag container creation (`computeChildrenForNewContainer`,
  nesting-preserving reparent of swallowed nodes)
- double-click / file-drop card creation (`parentIdAtPoint`)
- in-app copy/paste (`nodeClipboard.ts`'s id-remap through a copied-set map)
- ⌘/Ctrl+D duplicate (`duplicateNodes.ts`'s own, *different*, id-remap —
  duplicate needed to keep `parentId` when the parent wasn't duplicated,
  unlike paste, which had to strip it)
- container render/paint order (`renderOrder.ts`'s depth-first walk of the
  `parentId` hierarchy, since DOM order is the only z-index mechanism)

Over the course of one extended debugging session, each of these
independently produced its own real bug: auto-parenting didn't fire on
double-click/file-drop into a container; a ctrl-drag-created container
painted over what it had just enclosed; copy/paste of a container with a
child produced two unrelated nodes; ⌘/Ctrl+D had the identical defect;
⌘/Ctrl+D on a multi-level selection painted the duplicate interleaved with
the original instead of cleanly on top; and finally, a container being
actively dragged could render *behind* something it crossed mid-gesture,
because `parentId` (and so paint order) only updates at drop.

Each bug was fixed in turn, but the pattern was clear: **the formal-ownership
model required a bespoke fix at every mutation path**, because there were N
independent places that could each get "what belongs to what" wrong, rather
than one place that always recomputes it correctly. The user's own framing,
verbatim: *"this whole process of preserving parentage is feeling much more
convoluted, buggy, and brittle than the 'purely derive spatially' concept
that we had in the prototype."*

## The new (reverted) mechanism

Container membership is now **purely spatial, re-derived fresh every time
it's needed, never stored** — matching the original prototype's
`groupsContainingPoint`/`getContainedOrigins` (`Board.jsx`) exactly:

- `schema/node.ts`: `parentId` removed from the schema entirely. Schema
  version bumped to `2` (`schema/board.ts`); `schema/legacy.ts` strips a
  stray `parentId` from any older document and always stamps the current
  version on load.
- `containers/containment.ts` (renamed from `assignParent.ts`):
  `containersContainingPoint` (unchanged — was always pure geometry) plus
  a new `computeCarryIds(rect, excludeId, nodes)` — every node whose box
  overlaps `rect`, except a container that *fully encloses* it (the
  ancestor-exclusion fix a plain overlap test needs, ported from the
  prototype's `fullyEncloses`). One flat pass, no tree walk.
- `containers/renderOrder.ts`: the exact same depth-first pre-order
  traversal as before (already correct, already unit-tested) — only the
  source of the "parent" edge changed, from `node.parentId` to a freshly
  computed `immediateEnclosingParent` (the smallest-area other container
  that fully encloses it; on a tie — always true between a container and
  its own duplicate/paste, which only ever shifts x/y — the *later* one in
  the array wins, so a freshly-duplicated child attaches to its own
  freshly-duplicated parent rather than the original).
- `clipboard/nodeClipboard.ts` and `clipboard/duplicateNodes.ts`: both
  already applied one uniform offset to every copied/duplicated node's
  position (`pasteOffset.ts`'s staircase-then-push, and a fixed offset for
  duplicate) — this alone preserves relative spatial arrangement, and so
  containment, automatically. All that needed deleting was the `parentId`
  remap logic layered on top of an already-correct mechanism.
- `useBoardInteraction.ts`: `beginNodeDrag` now calls `computeCarryIds`
  once at drag-start (snapshot semantics unchanged — never recomputed
  mid-drag, matching the prototype); `handleNodePointerUp` no longer
  assigns anything on drop; ctrl/cmd-drag container creation no longer
  computes or assigns children — whatever a newly-drawn container
  geometrically encloses is picked up automatically the next time anything
  is dragged, and renders beneath it immediately via the geometric
  render-order fix above.
- `useCardCreation.ts`: `parentIdAtPoint` removed — every node-creation
  path (double-click, file-drop, paste-at-center) now uniformly does
  nothing beyond placing the node at a point; membership is automatic.
- The `bringToFrontAtom`/`bringDragToFrontOnce` fix (bringing a dragged
  node to the front of the array the instant a drag starts moving, so it
  paints above whatever it crosses for the whole gesture) is **orthogonal**
  to this whole change and was kept as-is — it's about z-order tie-breaking
  between siblings at the same nesting depth, which still matters
  regardless of how membership is determined.

See spec §2.3 (superseded/rewritten in place) and §7 for the
user-facing behavior this preserves exactly, and each touched file's own
doc comments for the mechanism-level detail.
